# Interface text

**Status: implemented.** The window speaks English and Chinese, each switchable
from the Settings page, and the choice is kept in the config file. The rules came
first because two of them - where a translated sentence may be assembled, and
what is deliberately left untranslated - decide the shape of the code rather than
the other way round.

What is in the program today:

- `crates/app/src/text.rs` - `Lang`, the `catalog!` macro, `Text::EN` /
  `Text::ZH`, `Text::PAIRS`, and the methods for sentences a value has to be
  slotted into.
- `crates/app/src/settings.rs` - the stored `lang`, `Settings::language()`,
  `Settings::text()` and `Settings::set_language()`, which writes before it
  switches.
- `crates/app/src/state.rs` - `AppState::language()`, `AppState::text()` and
  `AppState::set_language()`, and `Effect`, the enum that replaced the sentence a
  setting used to describe itself with.
- The Settings page's **Interface** card - the appearance chips and, beside them,
  the language chips.
- `crates/app/src/ui.rs` and the four dialog forms - every user-visible string,
  read from the table that is in force when the element is built.
- The app's own non-view modules - `core_detect`, `paths`, `reclaim`, `verifier`,
  `open_dir` and `settings` - which take `t: &Text` for the sentences they hand
  to the window. `main.rs` resolves the table once, right after the config file
  is read, so the notices produced before the window exists are already in the
  language it asked for.
- The command line and the diagnostics report - `cli.rs` and `diagnostics.rs`,
  which render the help, the refusals and the report in the language in force.
  `--help` is the one reader of the choice that cannot afford a full
  `Settings::load`, because loading would fold an older installation's config
  file into the data directory as a side effect of asking how the program is
  used; `settings::language_hint` reads the `lang` field and nothing else.

## One message, one place

A fixed label is a line in `catalog!`: the field name, the English, the Chinese.
The macro generates both tables from the same list, so a field added to one is a
compile error in the other - the two languages cannot drift apart in *shape*.

The other failure, a field copied across and never translated, is what
`every_message_is_translated` catches: a message identical in both languages
fails unless it is on an explicit allowlist of names that are the same on purpose
(`Xray PID`, `CDP port`, `SOCKS port`, `Brand`, `Share link`). A second test
asserts the catalog's size, so a table that shrank to nothing cannot pass
vacuously.

A label that is *not* in the catalog is a name rather than a sentence: `SOCKS5`,
`Chrome`, `Windows`, `macOS`, `Fingerprint Browser`, the `FP_BROWSER_*`
variables, the JavaScript property names on the Runtime Details panel, and the
`ss://, vmess://, vless:// or trojan://` example. A translated protocol name is a
worse bug than an untranslated one.

## Sentences are methods, not templates

Anything a number or a name goes into is a method on `Text`, not a field with a
`{}` in it. Word order is part of the translation, and the two languages do not
agree on where the number goes:

| English | Chinese |
| --- | --- |
| `Showing 3 of 12 profiles.` | `共 12 个档案，显示 3 个。` |
| `1 core, 2 proxies and 3 profiles` | `1 个内核、2 个代理和 3 个档案` |
| `Wrote 1 core, 2 proxies and 3 profiles to /x.json.` | `已写入 1 个内核、2 个代理和 3 个档案 到 /x.json。` |

English also needs plurals and Chinese does not, so the method is where that
stops being a caller's problem. The same reason bans a sentence stitched together
from translated fragments: "browser started (pid 12, cdp port 9222, socks port
1080)" is built in one place per language
(`Text::log_browser_started`), because a language that orders those clauses
differently cannot be served by an accumulator of pieces.

Joining is per-language too: `join_sentences` inserts a space between English
clauses and nothing between Chinese ones, because a Chinese full stop already
carries the break.

## Where the table comes from

Threading follows the rule the palette already uses, so "which language is this
rendering in" is answerable from a signature:

- **With a context**: `let t = self.state.text();` (an `AppView` method) or the
  table passed in from the caller (a free function with `cx`).
- **Without a context**: `t: &Text`, taken as the last parameter, exactly like
  `p: Palette`.

The dialog forms (`editor.rs`, `proxy_editor.rs`, `core_editor.rs`,
`proxy_import.rs`) are separate entities with no route to `AppState`, so they
**carry the table** - `text: &'static Text`, taken when they are opened. The cost
is that a language switched while a dialog is open reaches the next time it is
opened; the benefit is that no global had to be introduced.

The language is deliberately **not** a global, unlike the component theme. The
theme is a process-wide fact because the library has exactly one; the language is
a fact about one `AppState`. Tests run in parallel, each with its own language,
so a global would make every English assertion a race against whichever test
switched to Chinese first - and the answer to that race is serialising tests,
which is a gate that fails for reasons unrelated to the code.

## Identifiers do not move

`Page::id()` returns frozen English slugs (`Profiles`, `Proxies`, `Cores`, `Log`,
`Settings`) and the sidebar's element id is `nav-{id}`, while the visible name
comes from the table. Deriving an id from display text is the classic
localisation trap: switching the language would make the click target of every
test and every script built on top of them disappear.

`SettingKey::effect()` returns an `Effect` enum (`NextStart`, `Now`, `Derived`)
rather than the sentence that describes it, and `Effect::label(t)` is the
sentence. The application used to compare that value against the literal `"now"`;
a translated string compared for control flow would have made behaviour depend on
the language in force.

## What falls back, and what is refused

- No `lang` in the config file, an empty value, or a name this build does not
  know (`kl`) starts in **English** rather than refusing to start.
- `zh`, `zh-Hans` and `zh-CN` are the same language as far as this build is
  concerned. A region is not a different translation.
- The choice is written to the config file **before** the window switches, like
  the appearance and for the same reason: a file that cannot be written refuses
  the switch rather than showing a language that would be gone by the next start.
- The chips are labelled in their own language (`English` / `简体中文`), and those
  two words are not in the catalog. Someone who cannot read the language they are
  in can only find their way out through an endonym.

## Frame translated, evidence not

The window's own voice is translated. That includes the modules that are not the
view: the core detection notices (`core_detect`), the moved-data-directory note
(`paths`), the reclaim line about a previous run's leftovers (`reclaim`), the
verification line's address clause (`verifier`), the "not a directory yet" answer
(`open_dir`), and the config-file read and write frames (`settings`).

What is *not* translated is the innermost text those frames carry: the message
raised by `runtime`, `domain` or `storage`, a `serde_json` parse error, the
operating system's `io::Error`, or the exit status of `xdg-open`. The window
translates the frame it puts around them and leaves the account of the fault as
it was given:

| Translated frame | Left as it came |
| --- | --- |
| `无法读取指纹：` | `no such file or directory` |
| `无法写入 /home/u/.config/…：` | `permission denied (os error 13)` |
| `浏览器内核的可执行文件已缺失：…` | the path the user set |

The reason is that a bug report has to be matchable to a log. Re-writing an
engine's diagnosis into a second language would produce two different strings for
one event, and the one in the log would be the one nobody can search for.

The exception is `FaultClass`, a closed enum. It has a finite, known set of
values and the window uses it as a word rather than as an engine's account, so
`Text::fault_class` translates it.

The diagnostics report obeys the same split. Its headings, its labels and the
words it puts around a file's state (`missing`, `mode 0600`, `directory, 6
entries`) are translated; what it quotes - paths, the version, the commit, the
lines of the activity log, and the operating system's own `io::Error` - is not. A
translated path would not resolve, and a translated log line would not match the
file it came from.

## Open questions

- **Operating-system locale detection.** The window starts in English whatever
  the system is set to. Reading the locale is a decision about defaults, not a
  translation, and it was left out: it would have to be distinguishable from a
  stored choice that says English, and this build has no way to tell "never
  chosen" from "chosen English" in a file written before the switch existed.
- **A third language** is a line per message plus one arm per sentence method.
  Nothing in the design assumes two; `Lang::ALL` is what the switch iterates.
